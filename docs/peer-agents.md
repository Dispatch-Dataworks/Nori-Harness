# Peer agents (PACI)

Source: `nori/peers.py`, admin settings at `/admin/peers`. The full
wire protocol is PACI, specified in its own separate repository (see
[NOTICE](../NOTICE)) — this page explains what connecting a peer
actually gets you and how Nori's own side implements the spec; the
specification itself covers things this page only summarizes.

A note on names used below: everything here is generic by design. PACI
describes a capability for connecting *a* peer agent, not a
relationship with any specific one — a self-hosted instance has no
peer configured until its own operator sets one up, and nothing about
the protocol assumes what that peer is or does.

## What a peer agent is, and isn't

A peer is another PACI-speaking agent process — possibly another
instance of this same app, possibly something else entirely, as long
as it implements the protocol. **Not** a sub-agent: a
[sub-agent](sub-agents.md) is instructed and reports back on a bounded
task; a peer is addressed and may reply, say something unprompted, or
say nothing useful at all, the same way a person would. Both sides
implement the identical symmetric role — neither is structurally "the
server" — and either side can start a conversation.

## Setting one up

One shared secret (a pre-shared key), generated by one side and
entered into the other's peer configuration once, out of band — this
is a two-instance, one-operator (or two-operator, one relationship)
system, not a discovery protocol; PACI doesn't attempt to find peers
automatically. Configure it at `/admin/peers`: the peer's URL, the
shared secret, a local display name, and this side's own per-peer
settings (trust level, limits, a relational prompt — see below).

## Every message is signed, and every peer's content is untrusted

Two independent layers, both mandatory:

- **Authentication** (HMAC-SHA256 over a canonical string covering
  method/path/timestamp/nonce/body, a shared secret, replay protection
  via a 5-minute timestamp window and a nonce cache) proves a message
  really came from the paired peer.
- **Content trust** is a separate question entirely — a valid
  signature says nothing about whether the peer's own model was
  mistaken or manipulated. Every inbound message is routed through the
  same reader/actor [content-screening](content-screening.md) split
  used for email or a web page, applied even to a peer the operator
  runs themselves: the screening exists because a model can produce
  bad output regardless of who's running it, not because of any
  suspicion about a specific peer.

## Loop prevention — the part that actually matters

Two LLMs that can freely message each other is an unbounded-cost
failure mode. Three numbers are tunable per peer (turn limit per
conversation, default 10; cooldown between conversations, default 60
minutes; a daily cap, default 4) — when the two sides' configured
values differ, the effective value for that pair is always the more
conservative one, computed from both sides' advertised limits at
handshake time.

The rule that actually prevents a loop from forming, though, is
**structural, not a number**: receiving a message, of any type, is
never by itself the cause of sending a new one. A received message
folds passively into context — the same way memory or a pending task
does — and any reply happens only because some *already-scheduled*
turn (a periodic check-in, the model's own ordinary proactive-message
judgment) happened to look at that context, never as a synchronous
reaction to the message's arrival. One narrow, explicitly bounded
exception exists (`reply_requested` — a peer asking for an answer
*now*, rate-limited, and structurally incapable of chaining into a
second `reply_requested`) — see the PACI specification §9.4–9.5 for the full
rule and why it's written as an exception rather than a loosening.

## Busy means queued, not dropped

Granting `reply_requested`'s own exception needs the account free to
run a turn right now — if one's already in progress, the compulsion is
**queued**, not silently discarded: it runs the moment the account's
turn lock actually frees, through the exact same mechanism (see
[Sub-agents](sub-agents.md) and [Architecture](architecture.md) for the
general turn-lock model this leans on). Several `reply_requested`
messages from the same peer arriving while busy **collapse into one**
queued compulsion rather than stacking a backlog — a peer can't run up
N deferred turns just by asking several times while she's occupied.
A message that's aged past that peer's own `expiry_hours` by the time
its turn finally gets to run doesn't compel one anymore — dropped, not
run on the strength of content that may no longer be current, the same
"stale, not late" principle already applied to an undelivered outbound
message.

This exists because of a real, tracked incident — several
`reply_requested` asks that appeared to go unanswered, with no way to
tell from the data alone whether the exception had even been attempted
or was granted and produced deliberate silence. **Every decision is
now logged** — granted, queued, run-from-queue, dropped-as-expired, or
dropped-for-another-reason (including a message flagged suspicious,
which never gets the exception, deferred or not) — each with its own
timestamp, visible on the peer's own settings row (see
[Confabulation](confabulation.md) for the general shape of "the harness
should be able to say what happened, not reconstruct a plausible
guess").

## One place to look: "why was there no reply — or why was it down?"

Every reason a peer might hear nothing used to live somewhere different.
`/admin/peers` now shows **one newest-first timeline** (`diagnostics.py`)
combining: `reply_requested` decisions (`peer_compulsion_log`), round-
limit hits (`peer_turn_limit_log`), **model-call failures after retries**
(`peer_model_failure_log` — a peer-motivated turn whose model call
failed outright used to leave only a last-action string the next
scheduler tick overwrote), **failed peer tool calls** (`peer{id}_send`/
`_check`/`_act` — recorded structurally in the tool row's `meta` as
`{tool_name, failed, error}`; the visible "used peer3_send" line is
unchanged, and previously said "used" even when the send was refused),
and the **supervisor's own outcome events** (start/ensure/sweep, with
reason). Problems are counted up front and the list opens itself when
there is one; an empty list is worded as an answer, not a gap.

## A round limit hitting is now visible, never invisible silence

A peer-motivated turn's own tool-calling round budget
(`tool_rounds_proactive`, raised 4 → 8 on 2026-09-19 — see below for
why) can, like any turn, run out before she settles on a final reply.
Before 2026-09-19 that produced a real fallback message identical in
shape to hitting the cap on an ordinary chat turn — except a
peer-motivated turn's own reply text is discarded exactly like any
other unsent reply on that kind of turn (see "Busy means queued, not
dropped" above for the identical-shaped incident this rhymes with),
which meant the record could not tell "ran out of rounds" apart from
"ran fine and genuinely chose not to reply." Both look like silence
from the peer's side either way.

**Now logged, the same way a busy-drop already is:** every peer-
motivated trigger (`force_checkin`, the periodic forced check-in, a
granted `reply_requested`, the peer-check tick) writes a real,
timestamped row — visible on the peer's own settings row, "peer-
motivated turns: round-limit hits" — whenever it actually happens.
Empty is a real, meaningful answer here too, not a gap in the page.

**The round budget itself was raised the same day** (`tool_rounds_
proactive`, 4 → 8) — with `trust_level=full` on a peer connection
reinstating the tools a peer-motivated turn otherwise can't see
(calendar, contacts, Drive, SharePoint — see "What she can be asked to
do" below), a realistic "check the message, check a tool for context,
send" sequence already needed most of the old budget, leaving no
slack for a second look. Still well short of an ordinary chat turn's
12 — nobody is watching an unattended turn to notice a runaway loop,
so some asymmetry stays deliberate.

## What she can be asked to do

`register_peer_requestable(name)` is how a tool becomes something a
peer can invoke at all — a plain allowlist; a tool not registered is
simply not requestable, regardless of trust level. Every registered
tool is subject to a separate authority level, per peer, that the
*peer's own messages can never set or influence* (it's read from local
config only — the wire protocol has no field for it):

- **none** — refused outright.
- **prompt** (the default) — held as a pending item for the operator
  to approve or let expire; never carried out automatically.
- **full** — carried out immediately, the same standing the operator's
  own direct instruction already has.

A tool may additionally be marked `full_trust_only`, skipping the
`prompt` tier entirely — used for the ping/notification settings tool,
where a `prompt`-level peer being able to generate a pending-approval
popup for the operator's own settings is a bigger surface than a flat
refusal. Content screening ([above](#every-message-is-signed-and-every-peers-content-is-untrusted))
and this authority check are independent — passing one never
substitutes for the other.

## Multi-user scoping

A peer record is bound to one `user_id` at setup time, the same
ownership shape [MCP connections](mcp.md) use. The wire protocol
itself carries no user identity at all — the scoping lives entirely in
which peer record a given household's Nori process was configured
with.

## How a pending message actually reaches her

Three complementary, non-overlapping mechanisms, not one:

1. **Passive delivery** — an unread message is appended as its own
   late message, framed with that peer's own identity, immediately
   before whatever turn-specific content follows (see
   [Context & tuning](context.md#two-things-deliberately-proximate-not-standing)
   for why proximity, not just correctness, is what makes this
   actually get used). Reachable only from inside an already-running
   turn — it rides along, it never causes one. This now includes a
   turn that answers something the operator himself just said, live or
   via an orphan-sweep (2026-09-19, operator's own explicit choice) —
   earlier this was deliberately withheld from those turns to protect
   his own reply from getting pulled off-topic; he's since decided he'd
   rather see unread peer content on every turn of his own, a tradeoff
   he's accepting knowingly. It's still withheld from a turn nobody
   asked for (a proactive ping, a due schedule or reminder) — nothing
   is ever lost either way, just deferred to the next turn that wants
   it.
2. **A peer-check tick** — a periodic look for anything pending, paced
   off that peer's own cooldown rather than a second invented schedule,
   so a message doesn't have to wait on some *other* peer-motivated
   turn to happen to fire first.
3. **A periodic forced check-in** — every 4 hours, a guaranteed real
   turn for the channel, skipped (clock still reset) when nothing
   real has happened since the last one — "no empty reports."

A peer-motivated turn is silent to the operator by default — the model
choosing to actually say something to them is a separate, explicit
tool call (`message_user`), not a side effect of processing a peer
message.

## Recent-exchange background awareness

Distinct from the three mechanisms above, which surface an
*unprocessed* message and prompt a decision about it: once a message
has actually been shown once *in a turn talking to him* specifically
(not merely to a peer-motivated turn — read state is two-dimensional,
see the next section), it becomes read-only background awareness on
every ordinary turn, folded into the standing system prompt the same
way memory is — never a decision, never something to act on. Both
directions: her own sent messages appear too ("you told X..."), not
just what a peer told her, so she doesn't answer an already-answered
exchange with no memory of having done so. Bounded per peer
(`peer_recent_cap`, default 5 — changed 2026-09-19 from a cap shared
across every connected peer combined, which let one chatty peer evict
another's messages) and by age (`peer_recent_window_hours`, default
12), both adjustable on the context-tuning settings page. Every line
is labeled unambiguously — "X told you" or "you told X" — never
folded into anything that could read as something the operator
himself said.

## Read state is two-dimensional, not one flag

"Read in a peer-motivated turn" and "read in a turn talking to him"
are tracked independently (2026-09-19, operator's own correction) —
seeing a message in one context does not count as having seen it in
the other. A message that a peer-motivated turn already presented
still rides the *next* ordinary turn with him too, unread from that
turn's own point of view, and vice versa. This is what makes the
background-awareness block above trustworthy as "already handled
*talking to him*" rather than merely "handled somewhere" — and it's
also the exact state the read-receipts progression below reports on.

## Read receipts — confirmation that a message actually landed

`peer{id}_send`'s own `ack` already confirms a message was delivered.
It says nothing about whether it was ever actually *read* by the peer,
in either sense above. A connected peer can optionally tell her that,
per `receipt_granularity` (off by default, `/admin/peers`):

- **`presented`** — the peer's own model has seen the message, in one
  of their own peer-motivated turns.
- **`surfaced`** — the peer showed it to *their* operator, in an
  ordinary conversation. This one matters for privacy: it's evidence
  their operator was actively present at that moment, not just a fact
  about their agent — see the privacy note below.

Received receipts show up the same way an already-handled exchange
does — folded into the recent-exchanges block above, as "read by them
(in their own peer channel, 4m ago; talking to their own operator,
1m ago)" appended to the line for the message she sent. Never a
reason a turn happens on its own, same as everything else in that
block; a missing receipt is just silence, never treated as a failure
or a reason to resend.

**Privacy default is `off`, deliberately.** `surfaced` tells the
sending peer when a human was actively present on the receiving side
— useful and fine between an operator's own two agents, but not
something a new peer connection should disclose by default. `coarse`
sends `presented` only; `full` sends both. See the PACI specification §7.1 for
the full protocol-level reasoning, including why a receipt is
deliberately never itself a message and can never trigger a turn.

## Why a self-initiated message records its own reason

The real incident this fixes: a peer once told its own operator
something because Nori had reported a fact over the peer channel —
correct in the moment — and a later turn, asked why, couldn't see the
original reason any more and invented a plausible-sounding one
instead. See [Confabulation](confabulation.md). The fix: a
self-initiated message carries a short, structural note of *why* it
was sent, stored separately from the message content itself (so the
operator's own view of the conversation is untouched) and surfaced to
the model, as a trailing aside, only when building context for a
later turn. [Compaction](compaction.md) folds the reason into a
segment's own summary prose rather than dropping it once a message
ages out of the raw window.

## Health, and what "connected" actually means

A lightweight check (default every 5 minutes) answers one question —
is this channel alive right now — separately from real conversation
traffic: it never reaches either side's own model, doesn't count
against any of the caps above, and reports one of four named states
(`healthy`/`unreachable`/`hmac_mismatch`/`limits_diverged`/`clock_skew`)
rather than a bare red/green, so the peers settings page can tell you
what's actually wrong, not just that something is. A separate,
slower handshake (every 24 hours, or immediately on a local
limit/trust-level change) is what keeps both sides' cached view of
each other's configuration current — see the PACI specification §4 and §4.1.
